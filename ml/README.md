# ML-модуль — модель этапа 1, скоринг, фильтр зрелости, ранжирование

Зона ответственности Участника 2 (CLAUDE.md §6). Каталоги `/ml` и схема БД.
Контракт `shared/schema.py` и `shared/contracts.py` отсюда не меняется.

## Состав

| Файл | Что делает |
|---|---|
| `app/dataset.py` | Чтение датасета организаторов (.xlsx/.csv), нормализация шкал §1, разбор источников |
| `app/lexicon.py` | Словари маркеров: слабость / зрелость / хайп |
| `app/source_meta.py` | Тип и доверенность источника по домену (§2.7, §2.8) |
| `app/features.py` | Инженерные признаки. Один и тот же код для датасета и для `SignalDoc` |
| `app/train.py` | Обучение, метрики Precision/Recall/F1, важность признаков, артефакт |
| `app/model.py` | Инференс `score(doc) -> (score, why)` + вклады признаков |
| `app/maturity.py` | Фильтр зрелости и хайпа с обязательной `rejected_reason` (§2.10) |
| `app/ranking.py` | Ранжирование и ТОП-15 |
| `app/evaluate.py` | Оценка выдачи по открытому запросу — то, что проверяет заказчик (§0.4) |
| `app/main.py` | FastAPI: `/score`, `/score/batch`, `/rank`, `/model/info`, `/health` |
| `db/` | Схема PostgreSQL, миграции, сид — статус и открытый вопрос по схеме в [`db/README.md`](db/README.md) |
| `tests/smoke_ml.py` | Дымовой прогон без датасета и без обученной модели |

## Запуск локально

```bash
# 1. окружение (Python 3.11)
python -m venv .venv
.venv\Scripts\activate          # Windows;  Linux/macOS: source .venv/bin/activate
pip install -r ml/requirements.txt

# 2. дымовой прогон — работает сразу, без датасета и без модели
python -m ml.tests.smoke_ml

# 3. официальный датасет находится в data/official_dataset.xlsx, затем:
python -m ml.app.train --dataset data/official_dataset.xlsx

# 4. сервис
uvicorn ml.app.main:app --reload --port 8001
```

Все команды выполняются **из корня репозитория** — иначе не найдутся `shared/` и `data/`.

## Обучение

```bash
python -m ml.app.train                            # официальный XLSX + data/control
python -m ml.app.train --dataset data/official_dataset.xlsx  # явный путь
python -m ml.app.train --min-precision 0.8        # требование ТЗ по точности
```

На выходе:

* `ml/artifacts/model.joblib` — артефакт для инференса (в git не коммитится);
* `ml/reports/metrics.json` — метрики машиночитаемо;
* `ml/reports/metrics.md` — отчёт к сдаче: данные, проверка инсайта §1,
  выбор модели, Precision/Recall/F1 на hold-out и кросс-валидации, важность признаков,
  диагностика фильтра зрелости.

Код возврата `1`, если точность на hold-out ниже `--min-precision` — удобно для CI.

### Отрицательный класс

В датасете организаторов **только положительные примеры**. Отрицательный класс задан явно
каталогом `data/control/` (все `*.csv`) и версионируется в git — это часть методологии, а не
служебный файл. Подробности и правила ведения: `data/control/README.md`.

## Оценка выдачи по открытому запросу

Организаторы проверяют решение **открытым запросом**, а не метрикой классификатора: по
6 темам датасета выдача сверяется с самим датасетом, по остальным — экспертно (CLAUDE.md
§0.4). F1 этапа 1 самодекларируемый, а эти числа заказчик может воспроизвести.

```bash
python -m ml.app.evaluate                        # offline по всем темам датасета
python -m ml.app.evaluate --area Финтех          # одна тема
python -m ml.app.evaluate --mode live --api-url http://localhost
```

| Режим | Что проверяет | Что нужно |
|---|---|---|
| `offline` (по умолчанию) | скоринг, фильтр зрелости, ранжирование | только датасет и `data/control/` |
| `live` | весь путь целиком, включая живой поиск | поднятые сервисы `api` и `parser` |

В offline пул кандидатов — датасет плюс контрольная выборка, «запросом» выступает область.
В live запросы уходят на `POST /api/search`, и заголовки выдачи сверяются с названиями из
датасета по пересечению значимых слов (дословного совпадения от парсера ждать нельзя).

Отчёт: `ml/reports/open_query_eval.md` и `.json` — recall@15 и precision@15 по каждой теме,
согласованность порядка, сколько негативов просочилось в ТОП, что не попало в выдачу.

Текущие числа (offline, все 6 тем): **recall@15 = 90 %, precision@15 = 100 %,
порядок rho = **−0.671**. Recall 90 % — это потолок, а не недоработка: в некоторых темах
размечено 17 сигналов, а выдача отдаёт 15.

**Состав и порядок измеряются отдельно, и это не формальность.** Recall с precision
говорят про множество, а сдаём мы ранжированный список: если на первой позиции стоит
наименее интересный из пятнадцати, правильный состав не спасает. Порядок мерится
корреляцией Спирмена между позицией в выдаче и «Баллом» датасета (стадия + тренд, §0.3) —
единственной внешней истиной про приоритет. Позиция 1 лучшая, поэтому согласованность
означает отрицательное rho. Проверка эту разницу уже отработала: при прежней формуле
ранга состав был идеален (precision@15 = 100 %), а порядок — случайным (rho = −0.04) и
по теме Edge прямо перевёрнутым. Одна метрика полностью маскировала провал по другой,
см. раздел 7 в [METHODOLOGY.md](METHODOLOGY.md).

## База данных

```bash
export DATABASE_URL=postgresql://signals:<пароль>@localhost:5432/signals

python -m ml.db.migrate --status   # что применено
python -m ml.db.migrate            # применить
python -m ml.db.seed               # залить датасет и контрольную выборку
python -m ml.db.seed --truncate    # перед заливкой очистить размеченные строки
```

Таблицы: `documents` (кандидаты, поля один-в-один с `SignalDoc`), `sources` (полные
метаданные по §2.7), `signals` (история оценок — новая строка на каждый прогон модели).
Векторный поиск — `pgvector`, индекс HNSW по косинусной близости.

Размерность `documents.embedding` — **1024** (multilingual-e5-large). Если Участник 3
возьмёт e5-base (768), нужна миграция `003`: менять `001` после применения нельзя,
раннер это проверяет по контрольной сумме.

## API сервиса

| Метод | Путь | Статус |
|---|---|---|
| `POST` | `/score` | контракт из `shared/contracts.py` — **не менялся** |
| `POST` | `/score/batch` | контракт из `shared/contracts.py` — **не менялся** |
| `GET` | `/health` | `mock=true`, если артефакт модели не обучен |
| `GET` | `/model/info` | паспорт модели: тип, дата обучения, порог, метрики, признаки |
| `POST` | `/rank` | **новый**: ранжирование кандидатов в ТОП-15 + отклонённые с причиной |

`/rank` использует DTO, объявленные локально в `ml/app/main.py`, а не в
`shared/contracts.py`: этот файл импортируют `api` и `parser`, менять его в одиночку
нельзя (CLAUDE.md §5). Перенос в общий контракт — после согласования в чате.

## Деградация без обученной модели

Если `ml/artifacts/model.joblib` отсутствует, сервис **поднимается** и считает балл
прозрачными правилами с фиксированными весами (`FALLBACK_WEIGHTS` в `app/model.py`),
честно сообщая об этом в `/health` (`mock=true`) и в тексте объяснения. Демо не падает
из-за отсутствия артефакта.

## Переменные окружения

Все необязательные: без них работают значения по умолчанию из таблицы.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `MODEL_PATH` | `ml/artifacts/model.joblib` | Куда `train` пишет артефакт и откуда сервис его читает — **один путь на обе операции** |
| `OFFICIAL_DATASET_PATH` | `/app/data/official_dataset.xlsx` в Docker | Датасет организаторов |
| `NEGATIVE_DATA_PATH` | `data/control` | Отрицательный класс: каталог или один `.csv` |
| `ML_REPORTS_PATH` | `ml/reports` | Куда писать отчёты |
| `WEAK_SIGNAL_THRESHOLD` | `0.55` | Порог **только запасного режима**. Порог обученной модели берётся из артефакта и этой переменной не переопределяется: он откалиброван на out-of-fold под требование точности §1, и подмена числом из `compose` тихо ломает заявленные Precision/Recall. Мусор и значения вне (0, 1) игнорируются с предупреждением |
| `DATABASE_URL` | не задана | Обязательна для `ml.db.migrate` и `ml.db.seed`. Префикс `postgresql+psycopg://` срезается автоматически |

## Артефакт модели

В финальном Docker Compose модель обучается во время сборки `ml`-образа:

```bash
docker compose build --no-cache ml
docker compose up -d ml
```

`ml/Dockerfile` копирует `data/official_dataset.xlsx` и `data/control/` в build context, запускает `python -m ml.app.train`, а затем упаковывает `ml/artifacts/model.joblib` в тот же образ. Отдельного `ml-trainer` сервиса и общего volume для модели нет.

Если артефакт отсутствует, сервис технически умеет работать на прозрачном rule fallback, но финальная демонстрация должна использовать обученный артефакт; `/health` и `/model/info` показывают текущий режим.

## Что здесь сознательно НЕ делается

* **Не файн-тюнится LLM и не строится нейросеть** — 100 размеченных строк, требование
  интерпретируемости, прямой запрет CLAUDE.md §2.2 и §7.
* **Не используются TF-IDF-мешки и эмбеддинги в основной модели** — вклад такого признака
  нельзя показать словами, а жюри отдельно оценивает интерпретируемость.
* **Фильтр зрелости никогда не отклоняет молча** — `rejected_reason` заполняется всегда,
  с подстановкой конкретных фактов (§2.10, §7).
