# Схема БД: состояние, риски, открытый вопрос к команде

Зона Участника 2 (CLAUDE.md §6: «Каталоги `/ml`, схема БД»).

## Чем это запускается

```bash
# строку подключения задаёт docker-compose; в коде ключей нет (§5)
export DATABASE_URL=postgresql://signals:<пароль>@localhost:5432/signals

python -m ml.db.migrate --status    # что применено, ничего не меняет
python -m ml.db.migrate --dry-run   # что применилось бы
python -m ml.db.migrate             # применить
python -m ml.db.seed                # залить датасет + контрольную выборку
```

## Статус проверки: сервером не проверялось, настоящим парсером — да

PostgreSQL локально не поднят, Docker не установлен. Поэтому **`migrate` и `seed`
против живого сервера не запускались ни разу.** Это остаётся главным риском первого
прогона на стенде.

Что всё-таки проверено, и чем именно (`python -m ml.tests.smoke_ml`, 130 проверок):

| Раздел | Что проверяет |
|---|---|
| 11 | ENUM-значения совпадают с `shared/schema.py` посимвольно — единственное место, где кириллица может разойтись незаметно |
| 12 | логика раннера: порядок и нумерация миграций, устойчивость контрольных сумм, срез префикса `postgresql+psycopg://`, определение чужой схемы и проверка после применения |
| 13 | самописная статика SQL: индексы по существующим колонкам, закрытые `DO`-блоки, баланс скобок |
| 14 | совместимость с `db/init.sql`: блок совместимости в `001` покрывает всё, что требуют раннер и сид; разрушающих операций нет; сид умеет писать `companies` и в `TEXT[]`, и в `JSONB` |
| **15** | **разбор миграций настоящим парсером PostgreSQL** (`pglast` над `libpg_query` — тот же парсер, что внутри сервера) + символическое проигрывание DDL в двух сценариях: чистая база и база поверх `db/init.sql` |

Раздел 15 закрывает то, что раньше было честно записано как незакрытое: «синтаксическая
ошибка, которую ловит только сервер». `pglast` в этом окружении устанавливается
(`pip install pglast`, есть готовое колесо под Windows); прежняя запись о том, что pip
упирается в подмену TLS-сертификата, устарела — сеть работает. На стенде `pglast` не
нужен, поэтому в `ml/requirements.txt` его нет, а раздел 15 помечается пропущенным,
если пакета нет.

Чего раздел 15 **не** даёт: он проверяет синтаксис и состав колонок, но не поведение
сервера — права, блокировки, доступность расширения `vector`, фактические типы. Первый
запуск на живой базе всё ещё обязателен.

Требования окружения сверены с `docker-compose.yml`: образ `pgvector/pgvector:pg16` —
значит `CREATE EXTENSION vector` и синтаксис `CREATE TRIGGER ... EXECUTE FUNCTION`
(PostgreSQL 11+) доступны.

## Схему создают два файла — и теперь это не конфликт

`docker-compose.yml` монтирует `db/init.sql` в `/docker-entrypoint-initdb.d/`, и на
ветке `main` этот файл создаёт `documents` / `sources` / `signals` / `model_runs` при
инициализации контейнера — **раньше, чем кто-либо запустит миграции.** Все `CREATE TABLE`
в `001` идут с `IF NOT EXISTS`, поэтому они становятся no-op, и колонок, которых нет у
`init.sql`, в таблицах не окажется.

Раньше раннер на это **отказывался работать**. Отказ снят: `001_core_schema.sql` теперь
содержит **блок совместимости** — `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` на то, что
`/ml` требует сверх `init.sql`. На чистой базе это no-op, на базе `init.sql` — добавляет
недостающее. **Ни одна чужая колонка не меняется и не удаляется**, поэтому живые вставки
парсера продолжают работать без правок.

Полный список того, что `/ml` требует сверх `db/init.sql`:

| Объект | Зачем | Кто добавляет |
|---|---|---|
| `documents.origin` | `dataset` / `control` / `parser` — разделение обучающей выборки и живых данных | блок совместимости в `001` |
| `documents.label` | метка этапа 1 (1 — слабый сигнал, 0 — зрелая/хайп) | там же |
| `documents.points` | «Балл» заказчика (стадия+тренд, 3–7) | там же |
| `documents.created_at` | у `init.sql` есть только `updated_at` | там же |
| `sources.domain` | аудит доверенности по домену (§2.8) | там же |

И всё. **Таблицу `signals` `/ml` не читает и не пишет** — её заполняет
`parser/app/database.py`, то есть она целиком в зоне Участника 3, и её расхождения между
двумя файлами `/ml` не касаются. Это сильно сужает то, что выглядело как несовместимость
схем: реального пересечения — пять колонок, и все добавляются аддитивно.

Два расхождения в типах, которые блок совместимости исправить не может, закрыты иначе:

* **`companies`**: `TEXT[]` в `001` против `JSONB` в `init.sql`. `psycopg` адаптирует
  список Python в массив PostgreSQL, и в `JSONB` такая вставка падает. `ml/db/seed.py`
  спрашивает фактический тип у базы (`companies_expression`) и подставляет
  `%(companies)s` или `%(companies)s::jsonb` — сид работает на любой из двух схем.
* **размерность вектора**: вопрос закрыт, см. ниже.

### Размерность вектора: 384, вопрос закрыт

Было «1024 или 384 — цифру ставлю по ответу У1/У3». Ответ есть в коде:
`parser/app/embeddings.py` объявляет `MODEL_NAME = intfloat/multilingual-e5-small` и
`EMBED_DIM = 384`. Эмбеддинги считает и пишет **парсер**; `/ml` их не вычисляет и не
читает (модель этапа 1 работает на инженерных признаках, а не на эмбеддингах). Значит
размерность диктует парсер, и в `001` теперь `vector(384)`.

Раздел 15 дымового прогона сверяет цифру в миграции с `EMBED_DIM` парсера
автоматически — но только когда `parser/app/embeddings.py` доступен в дереве. На ветке
`ml` этого файла нет, поэтому сверка помечается пропущенной и **начинает работать после
слияния с `main`**. По той же причине сценарий «поверх `db/init.sql`» в разделе 15 на
ветке `ml` пока вырожденный: здесь лежит скелетный `init.sql` без таблиц. Против
настоящего файла с `origin/main` проигрывание выполнено вручную — все колонки
разрешаются, ни один индекс не остаётся без колонки.

## Миграции

| Файл | Что делает |
|---|---|
| `001_core_schema.sql` | ENUM-типы, `documents` / `sources` / `signals`, триггер `updated_at`, **блок совместимости с `db/init.sql`** |
| `002_indexes.sql` | индексы под реальные запросы, включая HNSW по вектору |
| `003_card_fields.sql` | поля итоговой карточки-инсайта (§8) |

`003_card_fields.sql` добавляет в `documents` ровно те поля, что появились в `SignalDoc`
и требуются по §8: `description`, `advantage`, `case_example`, `evidence_summary`,
`dataset_score`, `retrieval_score`, `model_version`, `model_mode`. Всё через
`ADD COLUMN IF NOT EXISTS`, повторный запуск безопасен. В схеме `init.sql` эти колонки
уже есть — тогда миграция просто ничего не делает. Заполняет их не модель этапа 1:
текст карточки генерирует LLM-сервис У3 строго по найденным источникам (§2.3),
`retrieval_score` приходит из поиска У1 — со стороны `/ml` это хранилище, а не вычисление.

## Что проверить на первом живом прогоне

Порядок — ровно такой, скрипт-обёртки нет намеренно (каждый шаг должен быть виден):

```bash
python -m ml.db.migrate --status     # ожидание: все три НЕ ПРИМЕНЕНА
python -m ml.db.migrate              # ожидание: применено 3; в логе — режим совместимости,
                                     # если таблицы создал db/init.sql
python -m ml.db.seed                 # ожидание: documents 100 dataset + 45 control,
                                     # sources 412 (посчитано по текущим data/raw и data/control)
python -m ml.db.migrate --status     # ожидание: все три «применена»
python -m ml.db.migrate              # ожидание: «Непринятых миграций нет»
```

Контроль результата в самой базе:

```sql
SELECT origin, count(*) FROM documents GROUP BY origin ORDER BY origin;
-- ожидание: control = 45, dataset = 100
SELECT count(*) FROM sources;                       -- ожидание: 412
SELECT count(*) FROM documents WHERE stage IS NULL OR trend IS NULL;  -- ожидание: 0
```
