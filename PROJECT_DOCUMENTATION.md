# Weak0x00 Signals — документация проекта

## Назначение

Система принимает технологическую тему, собирает live-источники, отбрасывает явный оффтоп и зрелые/шумовые кандидаты, оценивает ранний сигнал ML-моделью и формирует TOP-15.

Для каждого выбранного сигнала UI показывает карточку с объяснением слабости, релевантности и проверяемыми источниками.

## Основной pipeline

1. **Frontend** отправляет запрос в `/api/search`.
2. **Parser** параллельно собирает научные материалы из arXiv, OpenAlex и Crossref.
3. Результаты группируются по близкой теме, чтобы одна карточка могла иметь несколько источников.
4. Context gate проверяет связь с исходным запросом.
5. Trust layer и ML проверяют качество/зрелость и рассчитывают confidence.
6. Ranking формирует TOP-15 и переносит сработавшие признаки в `signal_markers`.
7. Frontend сразу показывает карточку; LLM-enrichment остаётся ленивым и не является обязательным для поиска.
8. При открытии полного отчёта отображаются источники, trust level, описание, преимущество, кейс и доказательная сводка.

## Контракт карточки

`SignalDoc` содержит:

* `why`
* `relevance_reason`
* `signal_markers`
* `source_agreement`
* `sources`
* `score`
* `stage`
* `trend`
* `dataset_score`
* `description`
* `advantage`
* `case_example`
* `evidence_summary`
* `model_mode`
* `model_version`

### Why vs relevance

Это два разных вопроса:

* `why` отвечает **почему найденный кандидат считается слабым сигналом**;
* `relevance_reason` отвечает **почему кандидат относится к исходной теме поиска**.

Так карточка не смешивает качество сигнала с тематической релевантностью.

## Несколько источников на одну тему

Поиск запускает все доступные научные коннекторы для одного запроса.

После этого `parser/app/main.py` выполняет тематическое объединение:

1. сначала проверяются точные и почти точные совпадения заголовков;
2. затем выполняется cross-source similarity по содержательным словам;
3. для объединения дополнительно требуется общий тематический контекст.

Это предотвращает автоматическое объединение разных тем внутри одного широкого пользовательского запроса.

В результате одна карточка сигнала может содержать несколько подтверждающих источников из arXiv, OpenAlex и Crossref.

## Формирование содержимого карточки

Карточка должна оставаться содержательной даже без настроенной LLM.

Серверный fallback:

1. извлекает 1–3 предложения из объединённых аннотаций arXiv/OpenAlex/Crossref;
2. формирует описание конкретной темы;
3. объясняет слабость сигнала через стадию, динамику и число связанных источников;
4. извлекает явно встречающиеся эффекты, например автоматизацию, повышение точности или снижение затрат;
5. пытается выделить реальный пилот, испытание или внедрение из аннотации;
6. сохраняет все найденные источники одной карточки вместе с их trust level.

Наличие настроенного LLM поэтому не является обязательным условием для получения содержательной карточки.

## Хранение новых полей карточки

Новые поля карточки (`relevance_reason`, `signal_markers`, `source_agreement`) являются частью `SignalDoc` и возвращаются непосредственно в результатах конкретного search job.

При открытии полного отчёта frontend сохраняет эти поля из снимка поиска, даже если DB-backed `/signal/{id}` возвращает старую версию схемы.

Это не требует миграции существующего PostgreSQL volume.

## Правило языка карточки

Для карточки сигнала исходный `title` сохраняется без перевода, чтобы пользователь мог точно сопоставить сигнал с первоисточником.

Все остальные текстовые поля карточки должны формироваться на русском языке:

* `description`
* `why`
* `advantage`
* `case_example`
* `evidence_summary`
* `relevance_reason`

При наличии выбранной LLM поле `description` является русским переводом или сжатым пересказом доступного содержания источника, а не копированием английского abstract.

Технические названия, аббревиатуры и собственные имена, например `YOLO11`, `CNN` и `arXiv`, сохраняются без перевода.

Если `LLM_REQUIRED=true`, недоступность LLM считается ошибкой обогащения карточки, а не поводом показывать пользователю английский текст.

Без LLM используется только русскоязычный fallback без вывода исходного английского abstract.

## ML-режим и версия

Каждый `SignalDoc` после ML-ранжирования должен содержать:

* `model_mode`
* `model_version`

Текущая обученная модель использует:

```text
model_mode: trained
model_version: logreg-l2-v4
```

В интерфейсе техническое значение режима `trained` отображается как:

```text
обученный
```

Версия модели отображается отдельно.

## Проверка

### Локальная проверка Python

После распаковки проекта выполнить:

```bash
python -m compileall parser/app api/app ml/app shared
python docs/check_project.py
```

### Проверка frontend

```bash
npm install
npm run build
```

### Полный стенд

```bash
docker compose up -d --build
```

После запуска необходимо выполнить несколько live-запросов и открыть несколько карточек.

Следует проверить:

* наличие нескольких источников в одной карточке;
* наличие `why`;
* наличие `relevance_reason`;
* наличие `signal_markers`;
* наличие `source_agreement`;
* наличие trust level для источников;
* наличие содержательного русского `description`;
* наличие `advantage`;
* наличие `case_example`;
* наличие `evidence_summary`;
* наличие `model_mode`;
* наличие `model_version`;
* отсутствие необходимости в LLM для базового формирования содержательной карточки.
